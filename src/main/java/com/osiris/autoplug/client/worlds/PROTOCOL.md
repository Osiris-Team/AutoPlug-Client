# Virtual worlds and dedicated server ownership

All source in this package is original MIT code. It imports neither HMCL nor another launcher's implementation. The native Minecraft client launcher remains the shared UI/CLI client execution path.

`WorldStore` saves definitions in `~/.autoplug/worlds/definitions/<id>.properties` and independent server installations/saves in `~/.autoplug/worlds/instances/<id>/`. Stable OS lock files live in `worlds/locks/` outside save data; deletion retains that lock until save and metadata removal finish, including on Windows. Launch acquires the same lock and re-reads metadata before preparing. The small lock files are retained so deleting/recreating a path cannot create competing lock inodes. A world records its source server profile, Minecraft version, loader, optional client profile and optional explicitly supplied executable JAR. Creation copies `plugins/` or `mods/`, `config/` and `defaultconfigs/`; immutable JAR assets use the existing content-addressed cache. Mutable configs are separate copies. Credentials and launcher account files are not copied. The profile collection is a creation-time snapshot: later profile updates do not overwrite an existing world's configs or save. The selected source profile must still exist and retain its recorded type/version/loader when playing. Deleted-source worlds remain visible and can still be deleted or inspected.

Client `MODS` profiles, plugin `PLUGINS` profiles and server `MODS_SERVER` profiles have separate active defaults. Both `mods-server` and `mods_server` are CLI aliases. Server mods use the existing profile updater, Modrinth exact-file lookup and configured CurseForge provider; migration retains the existing review/disabling transaction. Plugin worlds can generate an isolated vanilla client profile. Server mod worlds require an explicitly selected client `MODS` profile with the same game version and loader; copying server-only mods into the client would be unsafe.

World creation and launch reject known contradictory type/loader pairs: plugin profiles cannot name the Fabric/Quilt/Forge/NeoForge mod loaders, and server mod profiles cannot name Paper/Purpur/Spigot/Bukkit plugin servers. This prevents a nominally successful server launch that silently ignores the entire selected asset directory. Explicitly named custom/hybrid loaders remain available with a matching supplied executable.

An explicit acceptance action records the Minecraft EULA decision per world. Nothing downloads a server or writes `eula=true` during world creation, and neither the UI nor CLI may infer acceptance from owning a Minecraft account. Production launch checks the decision before preparing the server. Unit tests accept only a temporary original synthetic fixture world and never accept the owner's EULA or start Minecraft.

The production server installer uses the same official provider protocols as AutoPlug's existing server updater and the existing `LauncherDownloads` cache. It does not swap process-global server executable paths, updater YAML, `Server` state, `user.dir`, or the owner's existing installation:

| Server loader | Automatic source | Integrity and execution |
| --- | --- | --- |
| Paper | Stable build from `fill.papermc.io/v3/projects/paper/versions/<version>/builds` | Published SHA-256 and byte length; executable server JAR |
| Purpur | Successful version-specific build from `api.purpurmc.org/v2/purpur/<version>/latest` | Published MD5 over official HTTPS; pinned build download |
| Fabric | Stable version-compatible loader plus stable installer from `meta.fabricmc.net/v2/versions` | Official generated server-launcher HTTPS endpoint; it supplies no published checksum. Its bootstrap performs its normal server/library installation inside the world directory |
| Spigot and other server loaders | Explicitly supplied matching executable server JAR | Readable manifest `Main-Class`; existing `UtilsMinecraft` version detection rejects a detectable mismatch. JARs that do not expose a detectable game version rely on the user's explicit matching selection |

Paper's download service requires an identifying User-Agent with a contact URL; this implementation supplies AutoPlug's repository URL. Stable builds are selected only within the requested game version; an absent release reports a clear error and never substitutes another game version. See [Paper's downloads service documentation](https://docs.papermc.io/misc/downloads-service/), the existing repository `PaperUpdater`, `PurpurUpdater` and `FabricUpdater` adapters, and the captured provider fixtures in `src/test/resources/virtual-worlds/`.

Spigot BuildTools is rejected as an installer rather than misrepresented as a runnable server. Forge/NeoForge distributions that require installation, argument files or platform run scripts do not gain an automatic dedicated-server installation path from this change; a directly executable matching bootstrap/server JAR may be supplied. Client Forge/NeoForge support remains in the native launch engine. This distinction is displayed through the server preparation failure, not hidden behind a successful fixture.

Java is selected using the exact game's official Mojang metadata and the existing `ManagedJavaRuntime`, honoring the public Java overrides in client settings. A chosen server executable is copied into the world directory, so independent worlds do not replace one another's executable. `server.properties` preserves unrelated local values but sets the managed save path, chosen port, status ping, RCON/query disabling and binding. A normal world binds to `127.0.0.1`; explicit sharing at launch binds on the host interfaces so a router can forward to it. Explicit client offline testing permits an unauthenticated server only while bound to loopback. Sharing requires online authentication.

`VirtualWorldService` owns a per-world OS file lock, a real dedicated-server `ProcessBuilder`, a matching native client process and an injected UPnP mapping. Settings select either port `0` for an available port or a fixed preferred port, and explicitly allow or disallow UPnP. A configured occupied port reports an error rather than silently using another port. As with ordinary separate server processes there is a small bind race after releasing the temporary socket; bind/startup failures are cleaned up. Readiness reuses AutoPlug `MineStat` JSON status and checks the advertised Minecraft version. No production raw TCP Minecraft ping is introduced here.

Only after readiness does the service request sharing and launch the client at `127.0.0.1:<port>`. Sharing is an explicit launch action and is rejected before preparation when the UPnP preference is disabled. A UPnP failure retains local play and returns a clear `shareFailure()` notice with manual forwarding/tunnel/CGNAT guidance. A world launched on loopback must restart with Share enabled before forwarding can work. The mapping is injected, so lifecycle fixtures never discover or change the owner's router. The production mapper owns its finite lease and reports renewal/ownership failures through its join address.

Server output is continuously drained with at most 80 retained lines of 2,048 bytes each; client pipes are drained without retaining account-related output. When either child exits, client startup fails, readiness expires, startup is cancelled, Stop is requested, or the application closes, the service terminates the owned client, sends `stop` to the server, waits a bounded grace period, then destroys/forcibly destroys remaining processes and observed descendants. It closes the mapping and file lock and removes the active lifecycle. Pending preparation is interrupted and cannot install a child process into a cancelled lifecycle without immediate cleanup. Cancelling a pending client preparation closes any already owned mapping immediately, even if that preparation has not returned; the OS lock stays held until preparation's final cleanup so deleting or restarting cannot race its remaining work. Shutdown waits up to ten seconds in total for pending startup operations to finish ownership cleanup; it waits on operation completion, not on the reusable UI/executor thread itself. Router cleanup errors remain available through `cleanupFailure()`; a finite router lease additionally bounds a mapping after abnormal host termination. Headless one-shot world commands must wait for their returned client process and then close the lifecycle before parent process exit.

The tests include successful read-only production GET captures for Paper, Purpur, Fabric loaders and Fabric installers on 2026-10-03. `sources.json` records the exact URLs, times, response byte lengths, original response SHA-256, selected fixture SHA-256 and the explicit field/record reduction. Values in those fixtures are real API responses, not fabricated server metadata. Ordinary tests use those captures offline and an original synthetic server/client executable in real child JVMs. The synthetic server implements only enough status protocol to exercise the existing `MineStat`; it is not Minecraft. Tests cover preparation, direct connection, stream draining, graceful stop, mapping cleanup, readiness/server/client failure, startup cancellation, forced stop, preferred-port/UPnP settings and isolation. One-shot CLI bridge tests wait for the actual child client to exit and also fail the output consumer immediately after launch; both paths must clean up the server, client and mapping.

No production server artifact was executed, no paid Minecraft account was used, no owner EULA was accepted and no real router mapping was attempted as contributor validation. A complete client-authenticated game join and public-world accessibility still require the maintainer's real game/router environment. The captured metadata and real fixture processes support the implementation without claiming that those distinct live outcomes occurred.
